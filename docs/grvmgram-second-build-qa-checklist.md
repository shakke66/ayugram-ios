## Правила ведения в отдельном тестовом чате

1. Идти по ID сверху вниз, по одной карточке.
2. Перед тестом дать точный RU UI path, условия, шаги и expected.
3. После ответа менять только `Статус второго прогона` и `Результат второго прогона / что доработать`.
4. Старое наблюдение не редактировать: это historical defect первого билда.
5. При `🟡/❌` записать device/iOS, language, account/chat/topic scope, шаги и факт; PII закрыть.
6. Не использовать relaunch для «починки» live-сценария. Crash/freeze/media loss/duplicate notification/account mixing — немедленный `❌`.

### G01 — Мастер «Режим призрака»

- **Статус первого прогона:** 🟡 Надо доработать
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🔧 Доработано
- **Что изменено во втором билде:** Мастер больше не хранит отдельный runtime-gate: он вычисляется из четырёх surviving-компонентов, показывает `N/4`, массово включает/выключает их и использует общий snapshot текущего settings-store.
- **Что делает:** служит массовым переключателем и индикатором состояния отдельных Ghost-компонентов, но не является runtime-условием их работы. После удаления G07 управляет четырьмя компонентами и показывает `N/4`.
- **Как тестировать:** нажать мастер при `0/4` — включаются все четыре компонента и отображается `4/4`. Выключить один компонент — мастер автоматически гаснет и становится `3/4`, при этом оставшиеся три продолжают работать. Включить недостающий компонент вручную — мастер автоматически загорается. Нажать мастер для выключения — все компоненты становятся OFF. Дополнительно каждый компонент должен работать по собственному значению даже при выключенном мастере. После настройки на аккаунте A переключиться на B: значения должны сохраниться, поскольку GRVMgram-настройки глобальны для клиента.
- **Наблюдение первого прогона:** сейчас мастер является обязательным runtime gate: если верхний тумблер выключен, ни один включённый отдельный Ghost-компонент не действует. Требуется убрать эту зависимость: верхний тумблер только массово меняет значения и автоматически отражает состояние всех компонентов. Все проверки отдельных функций пользователь проводил с включённым мастером. Этот же неправильный gate делает недоступными read-actions `ST15–ST17`: `shouldSuppressReadReceipts` требует одновременно `ghostModeEnabled && suppressReadReceipts`; при выключенном мастере чат успевает очистить unread штатным чтением, suppression становится `false`, после чего пункты чтения не попадают в message/header menu. Также ранее подтверждён второй дефект: при смене Telegram-аккаунта загружается отдельный default snapshot, включая app icon; после возврата восстанавливаются значения основного аккаунта. Корневая причина account-scoped хранения уже подтверждена; нужен единый client-wide snapshot с миграцией, при сохранении изоляции архивов и других данных аккаунтов.
- **Результат второго прогона / что доработать:** _Заполнить._

### G02 — Закреплённые компоненты Ghost

- **Статус первого прогона:** 🗑️ Вырезать из форка
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🗑️ Удалено
- **Что изменено во втором билде:** Удалены locks schema/row/screen/counters/master exclusions; surviving Ghost — четыре компонента и `N/4`.
- **Что делает:** отдельный экран с пятью locks: «Отчёты о прочтении», «Просмотры историй», «Статус „в сети“», «Набор текста и загрузка», «Уход из сети после появления в сети». Если lock включён, мастер «Гост-режим» не изменяет соответствующий основной переключатель.
- **Как тестировать:** после удаления открыть: нижняя вкладка `Настройки` → `Настройки GRVMgram` → `Основное` → раздел `Гост-режим`. Строки `Закреплённые компоненты` и отдельного экрана locks быть не должно. Общий переключатель Ghost должен напрямую включать и выключать оставшиеся четыре компонента.
- **Наблюдение первого прогона:** принято продуктовое решение полностью удалить `Закреплённые компоненты` из iOS-версии. Это не соответствует назначению Desktop-функции, где закрепление даёт быстрый доступ к компонентам на боковой панели; применимого iOS-сценария для текущего механизма locks нет. Удалить строку, экран, счётчик `N/5` locks и саму логику исключения закреплённых компонентов из действия общего переключателя Ghost.
- **Результат второго прогона / что доработать:** _Заполнить._

- **Наблюдение первого прогона:** отчёты о прочтении и прослушивании успешно подавляются при включённом отдельном тумблере и текущем обязательном мастере Ghost. После исправления G01 повторно проверить независимую работу без master gate.

### G09 — Использовать отложку / Schedule Messages

- **Статус первого прогона:** ❌ Вообще не работает
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🔧 Доработано
- **Что изменено во втором билде:** Schedule Messages отвязан от удалённого G08 и stored master; политика применяется в реальном send pipeline по собственному значению.
- **Что делает:** при Ghost задерживает text/forward/existing media на 12 секунд, voice/round video на 17 секунд, новый файл по формуле `max(19, 13 + max(6, ceil(MiB × 0.7)))`; при proxy задержка умножается на `1.2` с округлением вверх.
- **Как тестировать:** сначала выключить мастер Ghost (`0/4`) и все четыре Ghost-компонента, включить только G09. С секундомером проверить: text, forward и уже существующее media — `12 s`; voice и round video — `17 s`; новый файл — `max(19, 13 + max(6, ceil(MiB × 0.7))) s`. При proxy каждое значение умножается на `1.2` и округляется вверх. Повторить при G09 OFF — искусственной задержки нет; затем включить только G05 при всё ещё выключенном мастере и убедиться, что G09 сохраняет те же timings. Stored master и удалённая G08 не должны влиять на результат.
- **Наблюдение первого прогона:** при ручной проверке с включённым мастером Ghost функция не дала заявленного эффекта. Требуется отдельное воспроизведение с фиксацией типа сообщения, фактического времени отправки и сочетания с G05 до поиска корневой причины. Целевой сценарий: совместно с «Не отправлять Online» автоматически отправлять исходящие как отложенные, чтобы не раскрывать Online.
- **Результат второго прогона / что доработать:** _Заполнить._

### G10 — Отправлять без звука

- **Статус первого прогона:** ❌ Вообще не работает
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🔧 Доработано
- **Что изменено во втором билде:** Silent policy перенесена в deepest enqueue transform: `Never`, `In Ghost`, `Always` работают для основного composer path; `In Ghost` определяется OR четырёх компонентов, explicit silent сохраняется.
- **Что делает:** режимы Never, In Ghost и Always управляют silent-флагом исходящих сообщений.
- **Как тестировать:** B включает звук уведомлений. Для `Never`, `In Ghost`, `Always` отправить с A обычный text, media и forward: сначала без активных Ghost-компонентов, затем с одним компонентом ON при выключенном мастере. `Never` всегда со звуком, `In Ghost` без звука только при OR хотя бы одного из четырёх компонентов, `Always` всегда без звука. Отдельно проверить штатное явное `Отправить без звука`: оно не должно ослабляться GRVM policy.
- **Наблюдение первого прогона:** по результату ручной проверки функция вообще не влияет на звук уведомления у получателя даже при включённом мастере Ghost. Перед исправлением нужно воспроизвести отдельно режимы Never, In Ghost и Always и зафиксировать outgoing silent-флаг, чтобы установить корневую причину.

### G11 — Предлагать Ghost перед просмотром Story

- **Статус первого прогона:** ✅ Хорошо сделано
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🛡️ Positive guard
- **Что изменено во втором билде:** Положительный guard после удаления master/locks: действие Enable Ghost перед Story включает только `suppressStoryReads`, обычный просмотр и prompt остаются достижимыми.
- **Что делает:** до первого view receipt показывает выбор Enable Ghost Mode или View Normally; один prompt на открытый Story-screen.
- **Как тестировать:** включить G11, выключить мастер Ghost и все G03–G06, подтвердив `0/4`. На новом Story-screen выбрать `Enable Ghost`: действие должно включить только G04, оставить мастер визуально OFF, показать `1/4` и открыть Story без появления A у B среди зрителей. ### F26A — Filter-aware догрузка истории

- **Статус первого прогона:** ❌ Вообще не работает
- **Статус второго прогона:** ⬜ Не проверено
- **Тип изменения:** 🔧 Доработано
- **Что изменено во втором билде:** Pagination использует raw boundaries, bounded backfill sparse/all-hidden pages и no-progress guards.
- **Что делает:** после удаления скрытых сообщений из текущего history window автоматически добирает следующие raw-страницы, пока экран не получит достаточное число видимых сообщений или пока история действительно не закончится; pagination продвигается по raw boundaries, а не только по surviving entries.
- **Как тестировать:** в тестовом личном чате подготовить более 100 сообщений. Последние 50 сообщений второго аккаунта должны содержать уникальный token `GRVM_PAGE_FILL`, более старые сообщения — не содержать его. Создать scoped normal filter по token и открыть нижнюю границу истории. Ожидается, что скрытые 50 сообщений не оставляют пустой экран: клиент автоматически догружает более старые видимые сообщения. Повторить sparse-вариант, оставив среди последних 50 одно-два несовпадающих сообщения, и убедиться, что прокрутка к старой истории продолжает продвигаться без зацикливания на одном anchor. Show Filtered возвращает скрытые записи, но не должен быть необходим для восстановления pagination. Self Shadow Ban в этом тесте не использовать.
- **Наблюдение первого прогона:** корневая причина подтверждена статической трассировкой. Начальный запрос history использует параметр `44`, затем GRVM-фильтр применяется только к уже загруженному `MessageHistoryView`; скрытые сообщения продолжают занимать места в raw-окне. Pagination запускается лишь при наличии `filteredEntries.first` и `filteredEntries.last`. Если не выжило ни одной записи, следующая страница вообще не запрашивается и UI показывает пустой chat при наличии raw history. При редком числе выживших запрос центрируется на surviving entry, поэтому может повторять тот же anchor и блокироваться как идентичный. Временного или date cutoff у фильтра нет: каждое сообщение проверяется, когда его страница попадает в память, но вся серверная история заранее не сканируется. Требуется ограниченный filter-aware backfill/refill по raw boundaries с защитой от повторения anchor и корректным завершением только на реальной границе истории. Сообщения при этом не удаляются из Telegram/Postbox.
